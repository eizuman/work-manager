# AGENTS.md

## Область действия

Эти правила действуют для всего репозитория. Проект — статическое клиентское веб-приложение без сборщика и серверной части. Рабочий код находится в `index.html`, `app.html`, `css/` и `js/`; проектная документация — в `README.md` и `docs/`.

Перед изменениями прочитайте как минимум:

- `README.md`;
- `docs/ARCHITECTURE.md`;
- `docs/DATA_MODEL.md`;
- `docs/DEVELOPMENT.md`;
- документ из `docs/`, относящийся к задаче.

## Архитектурные ограничения

- Сохраняйте проект статическим и совместимым с GitHub Pages: приложение должно работать из файлов, публикуемых непосредственно из репозитория, без обязательного серверного runtime.
- Не вводите обязательный этап сборки, транспиляции или генерации артефактов без отдельного согласованного архитектурного решения.
- Сохраняйте две точки входа: `index.html` для входа и `app.html` для приложения.
- JavaScript загружается обычными `<script>` в порядке, заданном в `app.html`. Учитывайте глобальные функции авторизации из `js/auth.js`, `Sheets`, модули и `App`.
- Все обращения к Google Sheets должны оставаться централизованными в `js/sheets.js`. UI-модули не должны самостоятельно формировать запросы Sheets API.
- Google Sheets — основной источник предметных данных. Изменение колонок, названий листов или сериализации считается миграцией данных и требует обновления `docs/DATA_MODEL.md` и стратегии совместимости.
- `localStorage` используется для OAuth-сессии, списка/выбора объектов и локального кэша настроек. Не переносите туда предметные данные вместо Google Sheets.
- Сохраняйте адаптивность интерфейса для мобильной и desktop-версии. Порог desktop layout сейчас равен `768px` и согласован между JS и CSS.
- Не ломайте существующие таблицы, созданные ранними версиями. Новые поля должны иметь безопасные значения по умолчанию, а новые листы — создаваться или проверяться явным образом.
- Не добавляйте секреты OAuth, refresh token, client secret или пользовательские access token в репозиторий. Публичный OAuth Client ID не является секретом, но его изменение должно быть обосновано и документировано.

## Требования к изменениям

- Сначала определите затронутые сущности, листы и модули.
- Делайте минимальное изменение в пределах задачи; не смешивайте функциональную правку с массовым рефакторингом или переформатированием.
- При изменении модели данных обновляйте `docs/DATA_MODEL.md`; при изменении модулей или потоков — `docs/ARCHITECTURE.md`; при изменении запуска, OAuth или публикации — `docs/DEVELOPMENT.md`.
- Для операций над несколькими листами явно учитывайте частичный отказ: Google Sheets API не обеспечивает транзакцию на уровне текущего прикладного workflow.
- При удалении или переименовании сущностей проверяйте ссылки `work_log.task_ids`, `purchases.task_id`, `tasks.tags` и `tasks.assignees`.
- Пользовательские значения, попадающие в HTML, должны экранироваться. Не расширяйте использование необработанного `innerHTML` для пользовательских данных.
- Ошибки Google API должны быть видимы пользователю для интерактивных операций; фоновые ошибки должны как минимум диагностироваться и не повреждать локальное состояние.
- Не утверждайте, что runtime-интеграция проверена, если тест выполнялся без реального OAuth-сеанса и тестовой таблицы.

## Зависимости

- Не добавляйте npm-пакеты, CDN-библиотеки, фреймворки или build tooling без доказанной необходимости.
- Перед добавлением зависимости проверьте, нельзя ли решить задачу существующим Vanilla JS, CSS и Web API.
- Любая новая зависимость должна иметь конкретную пользу, оценку размера/риска, совместимость с прямой публикацией на GitHub Pages и документированное решение в `docs/DECISIONS.md`.
- Не добавляйте зависимость только ради форматирования, небольшой утилиты, иконки или операции, уже реализуемой браузером.

## Проверки

Минимальная статическая проверка после изменения JavaScript:

```powershell
Get-ChildItem js\*.js | ForEach-Object { node --check $_.FullName }
```

Проверка рабочего дерева и отсутствия случайных изменений:

```powershell
git status --short
git diff --check
git diff --stat
```

Для UI- или интеграционных изменений дополнительно вручную проверьте через локальный HTTP-сервер:

- страницу входа на мобильной и desktop-ширине;
- переход `index.html` → `app.html`;
- переключение всех пяти модулей;
- открытие/закрытие bottom sheet и диалогов;
- затронутые CRUD-сценарии в отдельной тестовой Google-таблице;
- переключение объектов и повторную загрузку страницы.

Для изменений данных зафиксируйте до проверки резервную копию тестовой таблицы. Не используйте рабочие данные для разрушительных тестов.

## Git

- Перед работой проверяйте `git status --short --branch` и сохраняйте чужие незавершённые изменения.
- Не используйте `git reset --hard`, принудительный checkout, очистку неотслеживаемых файлов или переписывание истории без прямого запроса пользователя.
- Не коммитьте `.claude/`, локальные настройки, токены, выгрузки таблиц и тестовые данные.
- Один коммит должен описывать одно логическое изменение. Сообщение должно указывать подсистему и результат, например `Calendar: preserve task links when moving entry`.
- Не выполняйте `git push`, не создавайте тег или релиз без явного запроса.
- Перед коммитом просмотрите полный diff, выполните применимые проверки и убедитесь, что документация соответствует коду.

## Совместимость Google Sheets и GitHub Pages

- Все URL ресурсов должны корректно работать при размещении проекта в подкаталоге GitHub Pages; предпочитайте относительные пути.
- Не полагайтесь на server-side redirects, rewrite rules, environment variables сервера или закрытые API endpoints.
- OAuth origin опубликованного сайта должен быть добавлен в Authorized JavaScript Origins соответствующего Google OAuth Client ID.
- Не требуйте Drive scope, если функция реализуема текущим `spreadsheets` scope.
- Не изменяйте существующие названия листов и смысл колонок без плана миграции и обратной совместимости.
- Подключение существующей таблицы должно либо работать с поддерживаемой схемой, либо выдавать понятную диагностику, не повреждая данные.
