# Roadmap Work Manager

## Статус документа

Roadmap основан на текущем коде и техническом аудите. Runtime-интеграция с реальным OAuth-сеансом, внешними ACL и production spreadsheets не проверялась. Порядок задач рекомендован по риску; сроки и исполнители не назначены.

Документ не утверждает новую продуктовую или системную архитектуру. Точная текущая схема находится в [DATA_MODEL.md](DATA_MODEL.md), устройство приложения — в [ARCHITECTURE.md](ARCHITECTURE.md), доступные проверки — в [DEVELOPMENT.md](DEVELOPMENT.md).

Размеры: **S** — локальная правка; **M** — несколько связанных функций или сценариев; **L** — изменение сквозного workflow с миграционной или интеграционной проверкой.

## 1. Critical fixes

### CF-1. Запретить destructive restore после ошибки чтения backup

- **Статус:** реализовано в коде; runtime-проверка с реальным OAuth и тестовой таблицей ещё не выполнена.

- **Проблема до исправления:** `_readSheetRaw()` превращал любую ошибку API в пустой массив, а `restoreBackup()` после этого мог очистить исправный целевой лист.
- **Ожидаемый результат:** ошибка чтения, доступа или структуры backup останавливает restore до очистки текущих данных; пустой лист отличим от ошибки чтения.
- **Затрагиваемые модули:** `js/sheets.js` — `_readSheetRaw()`, `restoreBackup()`; `js/app.js` — `openRestoreSheet()`.
- **Риск:** критический — потеря данных активного объекта.
- **Размер:** M.
- **Зависимости:** отдельный test spreadsheet и проверяемый backup; текущая схема из `DATA_MODEL.md`.
- **Критерии готовности:** ошибки `403`, отсутствующий лист, недоступный spreadsheet и network failure не запускают очистку; действительно пустой лист восстанавливается как пустой; пользователь получает причину отказа.

### CF-2. Проверять полноту backup до регистрации и restore

- **Статус:** реализовано в коде; read-back проверка добавлена, runtime round-trip ещё не выполнен.

- **Проблема до исправления:** `createBackup()` использовал подавление ошибок `_readSheetRaw()` и мог зарегистрировать неполный backup как успешный.
- **Ожидаемый результат:** backup считается созданным только после успешного чтения и записи ожидаемого набора листов.
- **Затрагиваемые модули:** `js/sheets.js` — `_readSheetRaw()`, `createBackup()`, `listBackups()`; `js/app.js` — backup controls.
- **Риск:** критический — ложное ощущение восстановимости.
- **Размер:** M.
- **Зависимости:** CF-1; согласованный текущий состав backup-листов.
- **Критерии готовности:** сбой любого обязательного чтения/записи возвращает ошибку и не добавляет metadata успешного backup; успешный backup проверяется повторным чтением ожидаемых листов.

### CF-3. Не оставлять `_registry` пустым при неуспешной перезаписи

- **Проблема:** `saveObjectsRegistry()` сначала очищает `A:E`, затем отдельным запросом записывает список; второй запрос может завершиться ошибкой.
- **Ожидаемый результат:** неуспешная синхронизация не уничтожает последнюю доступную registry metadata и не показывается как успех.
- **Затрагиваемые модули:** `js/sheets.js` — `saveObjectsRegistry()`; `js/app.js` — `saveObjects()`, `syncObjectsFromRegistry()`, object management.
- **Риск:** высокий — потеря cross-device списка объектов.
- **Размер:** M.
- **Зависимости:** тест с двумя локальными наборами объектов и имитацией ошибки записи.
- **Критерии готовности:** ошибка записи после начала синхронизации не оставляет registry пустым; интерактивный sync сообщает об ошибке; фоновый sync не сообщает об успехе до завершения записи.

## 2. Reliability

### R-1. Пересчитывать сохранённый finance balance после удаления

- **Проблема:** `deleteFinanceEntry()` и `deleteWorkLog()` удаляют finance rows без `_recalcAllBalances()`.
- **Ожидаемый результат:** значения `finance.balance` соответствуют оставшимся операциям после любого удаления.
- **Затрагиваемые модули:** `js/sheets.js`; проверки отображения в `js/finance.js`.
- **Риск:** высокий — противоречивые финансовые данные в Google Sheets.
- **Размер:** S.
- **Зависимости:** фиксированная семантика типов `work`, `advance`, `payment`.
- **Критерии готовности:** удаление первой, средней и последней операции даёт воспроизводимую последовательность balance; удаление work log даёт тот же результат.

### R-2. Исключить ошибочное сопоставление work log и ручной finance entry

- **Проблема:** `_syncWorkFinance()` и `deleteWorkLog()` ищут строку по `type === "work"` и дате в `description`; ручная строка с теми же значениями может быть изменена или удалена.
- **Ожидаемый результат:** календарные операции изменяют только соответствующее автоматическое начисление.
- **Затрагиваемые модули:** `js/sheets.js`, `js/calendar.js`, `js/finance.js`; при изменении данных — `docs/DATA_MODEL.md`.
- **Риск:** высокий — изменение не той финансовой операции.
- **Размер:** L.
- **Зависимости:** отдельное решение о совместимости существующих строк; изменение модели не должно выполняться без согласованной миграции.
- **Критерии готовности:** ручная операция с описанием-даты не изменяется при сохранении/удалении work log; старые автоматические строки продолжают обрабатываться предсказуемо.

### R-3. Обрабатывать частичный отказ многошаговых календарных операций

- **Проблема:** `executeDrop()`, `openMoveTasksSheet()`, `openRescheduleSheet()` и смена даты сначала записывают target, затем изменяют или удаляют source и finance.
- **Ожидаемый результат:** после ошибки пользователь видит фактическое состояние, а source/target не остаются незаметно продублированными или частично перенесёнными.
- **Затрагиваемые модули:** `js/calendar.js`, `js/sheets.js`.
- **Риск:** высокий — дубли и рассинхронизация календаря с finance.
- **Размер:** L.
- **Зависимости:** R-1, R-2; тесты отказа после каждого API-шагa.
- **Критерии готовности:** для каждого шага переноса проверен искусственный отказ; UI после ошибки перечитывает данные; повтор операции не создаёт дополнительный дубль.

### R-4. Обрабатывать частичный отказ задачи и связанных закупок

- **Проблема:** task сохраняется до `Promise.all()` закупок; часть закупок может сохраниться, а повторная попытка новой формы — создать вторую задачу.
- **Ожидаемый результат:** ошибка закупки не маскируется как ошибка записи задачи, фактически сохранённые сущности известны пользователю, повтор не создаёт дубликаты.
- **Затрагиваемые модули:** `js/tasks.js`, `js/sheets.js`, `js/purchases.js`.
- **Риск:** средний/высокий — дубли задач и неполные закупки.
- **Размер:** M.
- **Зависимости:** тестовые ошибки для одной из нескольких закупок.
- **Критерии готовности:** отдельно проверены ошибка task и ошибка каждой purchase; UI перечитывает сохранённое состояние; повторная отправка не дублирует task.

### R-5. Исправить reorder задач при активных фильтрах

- **Проблема:** `saveNewOrder()` передаёт только видимые filtered IDs, а скрытые задачи сохраняют старые значения и могут получить совпадающий `order`.
- **Ожидаемый результат:** drag reorder не создаёт одинаковый или неоднозначный порядок полного списка.
- **Затрагиваемые модули:** `js/tasks.js` — filters, drag handlers, `saveNewOrder()`; `js/sheets.js` — `reorderTasks()`.
- **Риск:** средний — непредсказуемый порядок после снятия фильтра/reload.
- **Размер:** M.
- **Зависимости:** определённое поведение reorder при фильтре на основе текущего полного списка.
- **Критерии готовности:** порядок стабилен после reload и снятия каждого вида фильтра; значения order полного списка однозначны.

### R-6. Валидировать текущую схему подключаемого spreadsheet

- **Проблема:** существующий Sheet ID принимается без проверки пяти базовых листов и порядка ожидаемых данных.
- **Ожидаемый результат:** несовместимая таблица отклоняется понятной ошибкой до выполнения записей.
- **Затрагиваемые модули:** `js/app.js`, `js/sheets.js`; контракт — `docs/DATA_MODEL.md`.
- **Риск:** высокий — запись в неверную структуру или поздний отказ после выбора объекта.
- **Размер:** M.
- **Зависимости:** текущая схема; поддержка таблиц с заголовком `id` и без заголовка.
- **Критерии готовности:** проверены отсутствующий лист, неверное имя и очевидно несовместимая структура; проверка не изменяет spreadsheet; совместимые старые таблицы принимаются.

### R-7. Сделать auto-backup независимым для каждого объекта

- **Проблема:** один `last_auto_backup` блокирует auto-backup остальных объектов в тот же день.
- **Ожидаемый результат:** решение о ежедневном backup учитывает активный объект.
- **Затрагиваемые модули:** `js/app.js`, `localStorage`; документация состояния — `docs/DATA_MODEL.md`.
- **Риск:** средний — отсутствие ожидаемой копии части объектов.
- **Размер:** S.
- **Зависимости:** CF-1, CF-2.
- **Критерии готовности:** два объекта получают независимые backup в один день; повторный запуск для того же объекта не создаёт лишнюю дневную копию.

### R-8. Не подавлять API-ошибки как пустые данные

- **Проблема:** `getWorkers()`, `getSettings()`, `listBackups()`, task scheduling map и `reloadWorkers()` скрывают часть ошибок или заменяют их пустыми значениями.
- **Ожидаемый результат:** код различает пустые данные и ошибку; интерактивные сценарии сообщают об отказе.
- **Затрагиваемые модули:** `js/sheets.js`, `js/tasks.js`, `js/app.js`.
- **Риск:** средний — пользователь действует на ложном пустом состоянии.
- **Размер:** M.
- **Зависимости:** общий способ представления ошибок без добавления внешней зависимости.
- **Критерии готовности:** для каждого перечисленного чтения проверены empty/403/network cases; интерактивная ошибка видна, а существующие данные в UI не заменяются молча пустым массивом.

## 3. Security

### S-1. Устранить XSS через backup metadata

- **Проблема:** `openRestoreSheet()` вставляет `id`, `date`, `time`, `title` из `settings.backups` через `innerHTML` и HTML-атрибуты без экранирования.
- **Ожидаемый результат:** metadata отображается только как текст/безопасные атрибуты и не может выполнить HTML или JavaScript.
- **Затрагиваемые модули:** `js/app.js`, `js/sheets.js`.
- **Риск:** критический — выполнение кода в origin, где access token хранится в `localStorage`.
- **Размер:** S.
- **Зависимости:** тестовые metadata со спецсимволами, кавычками и HTML.
- **Критерии готовности:** payload в каждом поле отображается как текст; обработчик restore получает исходное безопасно сохранённое значение; CSP не используется как замена escaping.

### S-2. Защитить все Sheet-derived значения в HTML-атрибутах

- **Проблема:** IDs задач, тегов, работников, транзакций и закупок часто вставляются в `data-*` без attribute escaping; Google Sheets допускает ручное редактирование.
- **Ожидаемый результат:** ни одно значение из Sheets не меняет структуру HTML независимо от поля назначения.
- **Затрагиваемые модули:** `js/tasks.js`, `js/calendar.js`, `js/finance.js`, `js/purchases.js`, `js/app.js`.
- **Риск:** высокий — DOM injection/XSS при изменённых данных таблицы.
- **Размер:** M.
- **Зависимости:** инвентаризация всех HTML templates; S-3.
- **Критерии готовности:** проверены текстовые и attribute contexts; payloads с `"`, `<`, `>`, `&` не создают элементы/атрибуты; пользовательские сценарии продолжают находить ID.

### S-3. Устранить расхождения между функциями escaping

- **Проблема:** `_escHtml()` и несколько `escapeHtml()` дублируются и экранируют разные наборы символов.
- **Ожидаемый результат:** каждый HTML context использует единообразную проверенную обработку.
- **Затрагиваемые модули:** все UI-файлы в `js/`.
- **Риск:** высокий — повторное появление XSS при новых шаблонах.
- **Размер:** M.
- **Зависимости:** S-1, S-2; сохранение статической архитектуры без новой библиотеки.
- **Критерии готовности:** дублирующиеся реализации удалены или сведены к одному контракту; есть проверки text и attribute contexts.

### S-4. Зафиксировать проверенные границы OAuth и внешней конфигурации

- **Проблема:** email allow-list выполняется на клиенте, token хранится в `localStorage`; реальные origins, consent settings и Sheets ACL неизвестны из репозитория.
- **Ожидаемый результат:** проверены фактические production origins, scopes и права; документация не представляет client allow-list как серверную защиту.
- **Затрагиваемые модули:** `js/auth.js`, `index.html`, `app.html`, `docs/DEVELOPMENT.md`.
- **Риск:** высокий — неверные предположения о границе доступа.
- **Размер:** M.
- **Зависимости:** доступ к внешней Google Cloud/Sheets конфигурации; без него задача может быть выполнена только частично и помечена как непроверенная.
- **Критерии готовности:** origins/scopes/ACL проверены владельцем; результат и неизвестные ограничения записаны без токенов или секретов.

## 4. UX defects

### UX-1. Обновлять Tasks UI после изменения исполнителей

- **Проблема:** `window.TasksModule` не существует для top-level `const TasksModule`; `reloadWorkers()` не вызывается и сам не рендерит UI.
- **Ожидаемый результат:** добавление, переименование и удаление исполнителя отражается в задачах без полного reload страницы.
- **Затрагиваемые модули:** `js/app.js`, `js/tasks.js`.
- **Риск:** средний — устаревшие имена и фильтры в интерфейсе.
- **Размер:** S.
- **Зависимости:** фактическая classic-script модель из `ARCHITECTURE.md`.
- **Критерии готовности:** три операции worker обновляют task form, cards и filters; console errors отсутствуют.

### UX-2. Согласовать фильтры статистики с графиками

- **Проблема:** period filter меняет карточки, но `getWeeklyHours()` и `getDailyHoursThisMonth()` продолжают использовать собственные периоды и все work logs.
- **Ожидаемый результат:** UI явно и непротиворечиво показывает, к каким данным относится фильтр и каждый график.
- **Затрагиваемые модули:** `js/stats.js`, `css/styles.css` при необходимости подписи.
- **Риск:** средний — неверная интерпретация статистики.
- **Размер:** M.
- **Зависимости:** подтверждение ожидаемой семантики существующих фильтров; новых видов отчётов не требуется.
- **Критерии готовности:** all/year/month/custom проверены на одном наборе данных; карточки и графики не создают противоречивого впечатления о периоде.

### UX-3. Корректно показывать часы при исторических ставках

- **Проблема:** `finance.js:getTotalStats()` делит заработанную сумму на текущую ставку, несмотря на per-entry rate в `work_log`.
- **Ожидаемый результат:** отображаемые часы соответствуют фактическим work logs выбранного периода.
- **Затрагиваемые модули:** `js/finance.js`, `js/sheets.js` read API.
- **Риск:** средний — неверный финансовый агрегат.
- **Размер:** S.
- **Зависимости:** существующие `workLogs` уже загружаются finance module.
- **Критерии готовности:** набор с двумя разными ставками показывает сумму фактических часов; суммы начислений не меняются.

### UX-4. Устранить сдвиги между UTC и локальной датой

- **Проблема:** defaults и auto-backup используют `toISOString()`, а календарь — локальные компоненты `Date`.
- **Ожидаемый результат:** выбранная пользователем локальная дата не меняется около границы суток.
- **Затрагиваемые модули:** `js/sheets.js`, `js/app.js`, `js/finance.js`, `js/stats.js`, `js/calendar.js`.
- **Риск:** средний — запись или backup относятся не к ожидаемому дню.
- **Размер:** M.
- **Зависимости:** единое подтверждённое правило локальной календарной даты.
- **Критерии готовности:** проверены моменты до/после локальной полуночи и timezone с ненулевым offset; даты calendar, finance, stats и auto-backup согласованы.

### UX-5. Показывать причины интерактивных API-ошибок

- **Проблема:** часть UI показывает общее сообщение или пустой список без причины, включая task picker и restore list.
- **Ожидаемый результат:** пользователь отличает отсутствие данных, отсутствие доступа и временную сетевую ошибку.
- **Затрагиваемые модули:** `js/app.js`, `js/tasks.js`, `js/calendar.js`, `js/sheets.js`.
- **Риск:** средний — повторные действия и неверные решения пользователя.
- **Размер:** M.
- **Зависимости:** R-8.
- **Критерии готовности:** empty/403/network cases имеют разные состояния; технические сообщения не раскрывают token.

### UX-6. Исправить keyboard workflow overlays

- **Проблема:** custom dialogs и bottom sheets не реализуют полный focus trap, Escape и возврат фокуса.
- **Ожидаемый результат:** существующие формы и подтверждения доступны с клавиатуры без потери фокуса за overlay.
- **Затрагиваемые модули:** `js/app.js`, `app.html`, `css/styles.css`.
- **Риск:** средний — недоступность части интерфейса.
- **Размер:** M.
- **Зависимости:** текущие `showBottomSheet()`, `hideBottomSheet()`, `showConfirmDialog()`.
- **Критерии готовности:** Tab остаётся внутри активного overlay; Escape закрывает допустимые overlays; фокус возвращается инициатору; mobile touch не нарушен.

## 5. Maintainability

### M-1. Удалить или обосновать неиспользуемые объявления

- **Проблема:** не вызываются `getAccessToken()`, `getObjectCode()`, `isDesktop`, `_recalcBalances()`, `renderTagsManage()`; не используются `CONFIG.SPREADSHEET_ID` и `CONFIG.HOURLY_RATE`.
- **Ожидаемый результат:** код не содержит ложных точек расширения и дублирующей конфигурации.
- **Затрагиваемые модули:** `js/auth.js`, `js/app.js`, `js/sheets.js`, `js/tasks.js`.
- **Риск:** низкий — путаница и ошибочное использование устаревших путей.
- **Размер:** S.
- **Зависимости:** поиск всех runtime-обращений; отсутствие внешних consumers у глобальных функций должно быть подтверждено.
- **Критерии готовности:** каждое перечисленное объявление удалено либо имеет подтверждённого caller и назначение; syntax check проходит.

### M-2. Сократить дублирование CRUD-шаблонов и object creation

- **Проблема:** создание объекта реализовано в двух UI-потоках; finance/purchases имеют повторные delete handlers; SVG и inline styles повторяются.
- **Ожидаемый результат:** одинаковое действие использует один проверяемый workflow без изменения пользовательских функций.
- **Затрагиваемые модули:** `js/app.js`, `js/finance.js`, `js/purchases.js`, `js/tasks.js`, `css/styles.css`.
- **Риск:** средний — исправление одного пути не попадает во второй.
- **Размер:** M.
- **Зависимости:** regression checklist существующих mobile/desktop сценариев.
- **Критерии готовности:** нет двух реализаций одной Sheets-операции; оба UI-входа дают одинаковую валидацию и ошибки.

### M-3. Централизовать фактические наборы листов

- **Проблема:** `_BACKUP_SHEETS`, `ALL_SHEETS` и `DATA_SHEETS` объявлены отдельно; состав backup и restore уже различается.
- **Ожидаемый результат:** код явно различает текущий состав создания, backup и restore, не скрывая расхождение в локальных массивах.
- **Затрагиваемые модули:** `js/sheets.js`, `docs/DATA_MODEL.md`.
- **Риск:** средний — новый лист включён только в часть workflows.
- **Размер:** S.
- **Зависимости:** решение по подтверждённому составу полного restore; CF-1, CF-2.
- **Критерии готовности:** состав каждого workflow определён в одном месте и покрыт проверкой; документация совпадает с массивами.

### M-4. Снизить сложность крупнейших файлов без смены стека

- **Проблема:** `app.js`, `calendar.js`, `tasks.js`, `sheets.js` и `styles.css` объединяют несколько ответственностей и содержат повторяющиеся шаблоны.
- **Ожидаемый результат:** затронутые workflows можно изменять и проверять локально, сохраняя Vanilla JS, classic scripts и GitHub Pages compatibility.
- **Затрагиваемые модули:** перечисленные файлы и порядок scripts в `app.html`.
- **Риск:** средний — регрессии при любом крупном изменении.
- **Размер:** L.
- **Зависимости:** автоматические проверки M-5; отдельные небольшие refactor-коммиты.
- **Критерии готовности:** границы изменённых частей документированы; публичные globals и порядок загрузки сохранены либо явно обновлены; пользовательское поведение не изменилось.

### M-5. Добавить воспроизводимые проверки текущего поведения

- **Проблема:** есть только `node --check` и ручной smoke test; нет test runner, CI, lint или validators.
- **Ожидаемый результат:** критические data workflows и статические инварианты проверяются повторяемо на безопасном test object.
- **Затрагиваемые модули:** весь `js/`, test configuration, `docs/DEVELOPMENT.md`; production data не используется.
- **Риск:** высокий — исправления критических дефектов трудно доказать без регрессий.
- **Размер:** L.
- **Зависимости:** отдельный OAuth/test spreadsheet или изолированные mocks; добавление зависимостей подчиняется `AGENTS.md`.
- **Критерии готовности:** автоматизированы как минимум backup/restore failure, work/finance sync, filtered reorder и escaping; проверки запускаются документированной командой.

## 6. Documentation

### DOC-1. Поддерживать документацию вместе с исправлениями данных

- **Проблема:** `DATA_MODEL.md`, `ARCHITECTURE.md` и `DEVELOPMENT.md` описывают текущие ограничения; после исправлений они могут стать устаревшими.
- **Ожидаемый результат:** каждый merged fix обновляет только затронутый источник документации.
- **Затрагиваемые модули:** `README.md`, `docs/ARCHITECTURE.md`, `docs/DATA_MODEL.md`, `docs/DEVELOPMENT.md`, `docs/DECISIONS.md`, этот roadmap.
- **Риск:** средний — разработка снова опирается на неверный baseline.
- **Размер:** S на изменение.
- **Зависимости:** конкретная реализованная задача roadmap.
- **Критерии готовности:** названия функций, листов, ошибок и проверок сверены с итоговым кодом; неактуальная задача отмечена выполненной или удалена.

### DOC-2. Зафиксировать проверенные внешние настройки

- **Проблема:** GitHub Pages source, production origin, OAuth consent и Sheets ACL неизвестны из репозитория.
- **Ожидаемый результат:** проверенные значения и остающиеся неизвестными ограничения явно разделены; секреты и токены не документируются.
- **Затрагиваемые модули:** `docs/DEVELOPMENT.md`, при необходимости `README.md`.
- **Риск:** средний — локальная реализация корректна, но production login не воспроизводится.
- **Размер:** S.
- **Зависимости:** доступ владельца к GitHub и Google Cloud configuration.
- **Критерии готовности:** deployment source и разрешённые origins проверены владельцем; неизвестные ACL не представлены как подтверждённые.

### DOC-3. Документировать проверенное поведение backup/restore

- **Проблема:** текущий backup включает семь листов, restore — пять и отдельную ставку; пользователю не показана полная гарантия восстановления.
- **Ожидаемый результат:** документация точно соответствует поведению после CF-1/CF-2 и не называет частичный restore полным.
- **Затрагиваемые модули:** `docs/DATA_MODEL.md`, `docs/DEVELOPMENT.md`, UI-текст restore в `js/app.js`.
- **Риск:** высокий — неверные ожидания перед destructive operation.
- **Размер:** S.
- **Зависимости:** CF-1, CF-2 и решение о фактическом составе restore.
- **Критерии готовности:** список восстанавливаемых/невосстанавливаемых данных совпадает с кодом и проверен round-trip тестом.

## 7. Future product ideas

Эти пункты не являются утверждёнными функциями или обязательствами. Они включены только потому, что соответствующий задел уже присутствует в коде или документации; реализация требует отдельного решения пользователя.

### FP-1. Управление активностью исполнителя

- **Проблема:** сущность `worker` хранит поле `active`, но UI не позволяет его менять, а `getWorkers()` не фильтрует неактивных работников.
- **Ожидаемый результат:** до реализации принято явное решение — использовать существующее поле в продукте или удалить неиспользуемый задел.
- **Затрагиваемые модули:** `js/sheets.js`, `js/app.js`, `js/tasks.js`, `docs/DATA_MODEL.md`.
- **Риск:** низкий/средний — сейчас поле создаёт неоднозначное ожидание поведения.
- **Размер:** S для удаления задела; M для пользовательского управления.
- **Зависимости:** прямое продуктовое решение пользователя; политика отображения уже назначенных неактивных работников.
- **Критерии готовности:** выбран один вариант; поле и UI имеют согласованную семантику либо неиспользуемое поле больше не представлено как функция.

### FP-2. Импорт ранее выгруженного JSON

- **Проблема:** JSON export реализован, а обратного import workflow в коде нет; отсутствие импорта уже зафиксировано в `DEVELOPMENT.md`.
- **Ожидаемый результат:** до реализации принято явное продуктовое решение, нужен ли обратный импорт; текущий export не описывается как автоматически восстанавливаемый файл.
- **Затрагиваемые модули:** `js/app.js`, `js/sheets.js`, `docs/DEVELOPMENT.md`, `docs/DATA_MODEL.md`.
- **Риск:** высокий при реализации — импорт способен массово изменить данные.
- **Размер:** L.
- **Зависимости:** прямой запрос пользователя, валидация текущей схемы, CF-1/CF-2, безопасный test object.
- **Критерии готовности:** без отдельного решения задача остаётся только идеей; при одобрении критерии импорта и восстановления определяются до изменения кода.
