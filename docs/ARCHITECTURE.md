# Архитектура Work Manager

## Назначение и границы

Work Manager — адаптивное клиентское приложение для учёта работ по объектам: календаря и времени, финансов, задач, закупок и статистики. Оно состоит из статических файлов и взаимодействует с Google напрямую из браузера. Активная внешняя публикация репозиторием не подтверждается; README исходной версии называет GitHub Pages.

В репозитории нет backend, базы данных, сборщика, package manifest и обязательного runtime кроме браузера. Google Sheets выполняет роль постоянного хранилища, Google Identity Services — роль OAuth-клиента.

## Структура приложения

```text
index.html                    страница входа
  └─ js/auth.js              OAuth и локальная сессия

app.html                     оболочка приложения
  ├─ js/auth.js              проверка срока токена и выход
  ├─ js/sheets.js            data-access layer
  ├─ js/calendar.js          календарь
  ├─ js/finance.js           финансы
  ├─ js/tasks.js             задачи
  ├─ js/purchases.js         закупки
  ├─ js/stats.js             статистика
  └─ js/app.js               orchestration и общий UI

css/styles.css               общий mobile/desktop дизайн
```

Скрипты являются обычными classic scripts, не ES modules. Фактический порядок в `app.html`:

1. Google Identity Services (`async defer`, в `head`);
2. `auth.js`;
3. `sheets.js`;
4. `calendar.js`;
5. `finance.js`;
6. `tasks.js`;
7. `purchases.js`;
8. `stats.js`;
9. `app.js`.

Порядок значим: `app.js` использует созданные ранее `CalendarModule`, `FinanceModule`, `TasksModule`, `PurchasesModule`, `StatsModule`, функции авторизации и `Sheets`.

`Sheets` и `App` явно экспортируются как `window.Sheets` и `window.App`. Пять `*Module` объявлены верхнеуровневыми `const`: они доступны последующим classic scripts через общий global lexical environment, но не создают одноимённые свойства `window`. Поэтому проверки `window.TasksModule` в текущем `app.js` не соответствуют способу объявления `TasksModule` и не выполняют предусмотренный вызов `reloadWorkers()`.

## Страницы и оболочка

### `index.html`

Содержит кнопку Google Sign-In, контейнер ошибки и loading overlay. `auth.js` ждёт загрузки Google Identity Services, создаёт OAuth token client и после успешной проверки аккаунта переводит пользователя на `app.html`.

### `app.html`

Содержит:

- desktop sidebar;
- mobile header и bottom navigation;
- пять контейнеров модулей;
- общий bottom sheet;
- confirm dialog;
- overlay выбора объекта;
- toast и loading overlay.

Контент модулей генерируется JavaScript во время выполнения.

## Модули

### `js/auth.js`

- хранит публичную OAuth-конфигурацию;
- инициирует token flow через `google.accounts.oauth2.initTokenClient`;
- запрашивает профиль через Google UserInfo API;
- допускает только настроенный email;
- хранит access token и срок действия в `localStorage`;
- выполняет silent re-auth для ранее известного пользователя;
- выполняет повторный token flow внутри открытого `app.html`, не уничтожая DOM формы;
- отзывает токен при выходе.

Это клиентская проверка доступа. Код не содержит собственного серверного механизма авторизации. Фактические права реального аккаунта и ACL таблиц из репозитория неизвестны.

### `js/app.js`

Главный контроллер:

- проверяет локальный срок OAuth-токена;
- синхронизирует registry объектов;
- выполняет миграцию legacy-объекта;
- выбирает активный объект;
- синхронизирует ставку;
- запускает авто-бэкап;
- переключает модули;
- предоставляет общий UI API через `window.App`;
- управляет объектами, исполнителями, настройками и восстановлением.

Публичный `App` содержит UI helpers, обработку ошибок, форматирование дат/сумм и чтение/запись локальной ставки.

### `js/sheets.js`

Единый слой доступа к данным:

- добавляет Bearer token ко всем запросам;
- при истёкшем токене или `401` инициирует событие повторной авторизации без перехода со страницы;
- читает диапазоны `A:Z` и кэширует строки в памяти;
- вычисляет физический индекс строки;
- добавляет, изменяет и удаляет строки;
- преобразует массивы ячеек в доменные объекты и обратно;
- синхронизирует календарные начисления с финансами;
- создаёт таблицы объектов и бэкапы, повторно проверяя скопированные листы до регистрации backup metadata;
- обслуживает registry, workers и settings.

Только этот файл должен знать URL и детали Google Sheets API.

### `js/calendar.js`

Отображает календарный месяц и одну запись `work_log` на дату. Запись может быть:

- фактом с часами;
- планом с чек-листом без часов;
- заметкой без работ и часов.

Модуль поддерживает изменение даты, перенос записей и пунктов, drag-and-drop чек-листа, привязку пунктов к задачам и расчёт суммы по ставке.

### `js/finance.js`

Показывает начисления за работу и выплаты типов `advance`/`payment`. Содержит фильтры по периоду, агрегаты и CRUD транзакций. Начисления из календаря попадают в этот же лист через `sheets.js`.

### `js/tasks.js`

Управляет задачами, статусами, погодой, тегами, исполнителями и ручным порядком. Позволяет создать связанные закупки и запланировать задачу на дату в календаре.

### `js/purchases.js`

Управляет позициями к покупке и купленными позициями. Покупка может ссылаться на задачу через `task_id`.

### `js/stats.js`

Читает `work_log`, вычисляет часы/рабочие дни/средние значения и рисует графики через нативный Canvas API. Внешняя chart library не используется.

## Потоки данных

### Авторизация

```text
Google Identity Services
  → access token
  → Google UserInfo
  → проверка разрешённого email
  → localStorage
  → app.html
```

Access token не передаётся собственному серверу, поскольку сервер отсутствует.

Если token истёк в уже открытом приложении, отдельный session overlay блокирует дальнейшую отправку, но сохраняет открытую форму в DOM. После успешного Google token flow пользователь повторно запускает сохранение вручную; многошаговая операция автоматически не повторяется.

### Загрузка приложения

```text
localStorage token
  → registry в legacy spreadsheet
  → merge с локальным списком объектов
  → activeObjectId
  → settings выбранного spreadsheet
  → CalendarModule.init()
```

### CRUD предметных данных

```text
UI event
  → метод модуля
  → Sheets domain method
  → row serializer
  → Google Sheets API
  → invalidation in-memory cache
  → обновление локального массива модуля
  → render()
```

Модули загружают данные при инициализации; часть чтений использует memory cache `sheets.js`, а календарь запрашивает `work_log` с force refresh. После записи `sheets.js` удаляет кэш затронутого листа.

### Календарь и финансы

При сохранении `work_log` с `hours > 0` рассчитывается `amount = hours × rate`. Затем `sheets.js` создаёт или обновляет строку `finance` типа `work`. Текущая связь определяется датой, записанной в `finance.description`; отдельного внешнего ключа пока нет.

### Задачи, календарь и закупки

- `tasks.id` сохраняется в `work_log.task_ids` для соответствующего пункта чек-листа.
- `purchases.task_id` связывает покупку с задачей.
- удаление родительской сущности сейчас не выполняет каскадную очистку ссылок.

### Несколько объектов

Каждый объект имеет отдельный spreadsheet. В `localStorage.objects` сохраняются metadata объектов, а общий лист `_registry` legacy-таблицы синхронизирует их между устройствами. Переключение объекта меняет `activeObjectId`, очищает memory cache и повторно инициализирует активный модуль.

Ключи `_cache` и `_sheetIds` в `sheets.js` не содержат spreadsheet ID, поэтому полная invalidation при переключении объекта обязательна для текущей реализации.

## Инварианты и ограничения runtime

- `saveWorkLog()` рассматривает дату как уникальный логический ключ и обновляет первую найденную запись этой даты. Ограничения уникальности на уровне Google Sheets нет.
- Append вычисляет следующую строку по числу заполненных ячеек колонки A; корректность алгоритма зависит от заполненного ID в колонке A.
- Автоматически созданные object spreadsheets не содержат заголовков. Reader пропускает первую строку только если её первая ячейка равна `id` без учёта регистра.
- При подключении существующего Sheet ID полная схема предварительно не проверяется. Автоматический ensure реализован для `_registry`, `workers` и `settings`, но не для пяти базовых предметных листов.
- Связь календарного начисления и finance основана на типе `work` и дате в `finance.description`; отдельного внешнего ключа нет.
- Многошаговые workflows выполняются последовательными API-запросами без прикладной транзакции.
- Restore полностью читает обязательные листы backup до первой очистки целевых данных; ошибка API не трактуется как пустой лист. Последующая очистка и запись целевых листов остаётся нетранзакционной.

Точный контракт листов и связей находится только в [DATA_MODEL.md](DATA_MODEL.md); инструкции запуска и внешней настройки — в [DEVELOPMENT.md](DEVELOPMENT.md).

## Интеграции

| Интеграция | Назначение |
|---|---|
| Google Identity Services | OAuth access token |
| Google UserInfo API | Email и имя пользователя |
| Google Sheets API v4 | CRUD, metadata, batchUpdate, создание spreadsheet |
| GitHub Pages | Hosting, заявленный в README исходной версии; активная конфигурация не хранится в репозитории |
| Browser Web APIs | localStorage, Fetch, Canvas, touch/drag events, Blob download |

Текущие scopes: `spreadsheets`, `userinfo.email`, `userinfo.profile`. Drive scope не требуется: бэкап создаётся как новый spreadsheet через Sheets API.

## Ключевые технические решения

- Vanilla JS и отсутствие build step сохраняют простую публикацию на GitHub Pages.
- Google Sheets используется одновременно как хранилище и таблица, доступная через Google API.
- Один spreadsheet используется для каждого объекта.
- Общий legacy spreadsheet остаётся registry для cross-device синхронизации.
- Локальный access token обеспечивает продолжение сессии после перезапуска браузера; это одновременно security-риск, который должен учитываться отдельно.
- UI строится повторным рендерингом HTML строками вместо компонентного framework.
- Данные совместимы со старыми строками за счёт значений по умолчанию при десериализации.

Подтверждённая кодом и Git-историей эволюция решений зафиксирована в [DECISIONS.md](DECISIONS.md). Ограничения модели описаны в [DATA_MODEL.md](DATA_MODEL.md).
