# Архитектурные решения

## Формат и достоверность

Этот документ фиксирует решения, подтверждаемые текущим кодом и Git-историей. Даты — даты коммитов, а не обязательно момент первоначального обсуждения. Мотивация не приписывается решению, если она не указана в commit message или комментарии к коду. Точная текущая схема не повторяется здесь и описана в [DATA_MODEL.md](DATA_MODEL.md).

Статусы:

- **принято** — решение действует в текущем коде;
- **эволюционировало** — решение сохраняется, но реализация менялась;
- **ограничение** — фактическое поведение, которое нельзя считать окончательным целевым дизайном.

## D-001. Статическое приложение на Vanilla JS

- Статус: принято.
- Зафиксировано: 30 апреля 2026, `3fabede` — `Add Work Manager app — full Vanilla JS build`.

Приложение состоит из HTML, CSS и обычных JavaScript-файлов без package manager, bundler и backend. README исходной версии указывает GitHub Pages; активная конфигурация Pages репозиторием не подтверждается.

Следствие: порядок `<script>` значим, модули используют глобальное пространство имён, а secrets/server-side enforcement недоступны.

## D-002. Google Sheets как основное хранилище

- Статус: принято.
- Зафиксировано: первоначальной реализацией и README от 30 апреля 2026.

Все предметные данные хранятся в именованных листах Google Sheets. Браузер вызывает Sheets API напрямую с OAuth access token.

Следствие: пользователь может просматривать данные вне приложения; одновременно отсутствуют транзакции, внешние ключи и контролируемые сервером миграции.

## D-003. Централизованный Sheets data-access layer

- Статус: принято.

Вся работа с API, кэшем, физическими строками и сериализацией сосредоточена в `js/sheets.js`. UI-модули вызывают доменные методы `Sheets`.

Следствие: изменения схемы должны проходить через row mappers в одном файле; прямые запросы API из UI будут нарушать установленную границу.

## D-004. Две страницы: login и application shell

- Статус: принято.

`index.html` отвечает за token flow, `app.html` — за приложение. Неавторизованный пользователь перенаправляется на login page, успешный вход — на app page.

Следствие: приложение не использует client router; ссылки и redirect должны оставаться совместимыми со статическим hosting.

## D-005. Клиентский allow-list одного Google email

- Статус: принято с ограничением.

После token response приложение запрашивает UserInfo и сравнивает email с `CONFIG.ALLOWED_EMAIL`. Чужой token отзывается.

Это клиентская проверка, а не самостоятельная server-side защита. Фактические права аккаунта на реальные spreadsheets репозиторием не подтверждаются.

## D-006. Desktop layout поверх mobile-first приложения

- Статус: принято.
- Зафиксировано: 30 апреля 2026, `6264e2d` — desktop sidebar, table views и responsive modules.
- Существенная mobile переработка: 2 мая 2026, `496e699`.

Одна кодовая база обслуживает mobile bottom navigation и desktop sidebar. Desktop layout включается при viewport не меньше 768 px по ширине и 600 px по высоте, чтобы мобильные устройства в горизонтальной ориентации сохраняли mobile layout.

Следствие: UI-изменения должны проверяться в обоих режимах; нельзя считать один layout производным и непроверяемым.

## D-007. Ставка хранится в настройках и в каждой записи работы

- Статус: эволюционировало.
- 30 апреля 2026, `7b5e1af`: per-entry hourly rate и settings.
- 2 мая 2026, `4d1aeeb`: синхронизация `hourly_rate` через Google Sheets.

Текущая ставка синхронизируется в листе `settings` и кэшируется локально. Каждая запись `work_log` сохраняет собственную ставку, а `amount` рассчитывается при сохранении записи.

Legacy-строки без rate читаются со значением 700.

## D-008. Чек-лист календаря сериализуется в строке

- Статус: принято с известным ограничением.
- Зафиксировано: 1 мая 2026, `05610f4` — checklist и plan day.
- 5 мая 2026, `b21b18c` — drag-and-drop порядка пунктов.

Пункты хранятся в `work_log.description`, разделённые `|`; выполненный пункт начинается с `✓`. Отдельный лист checklist в коде отсутствует.

Следствие: разделители не экранируются, а структурные изменения чек-листа требуют осторожной миграции.

## D-009. Начисления работы синхронизируются с finance

- Статус: принято с известным ограничением.

Сохранение фактических часов создаёт/обновляет finance entry типа `work`. План без часов не имеет начисления. Связь ищется по дате в `finance.description`.

Следствие: связь неустойчива к ручным операциям с теми же type/description; стабильный source ID в текущей схеме отсутствует.

## D-010. Явная запись в следующую строку вместо `values:append`

- Статус: принято.
- Зафиксировано: 1 мая 2026, `dca11b5` — замена `:append INSERT_ROWS` на запись по row count.

Код считает заполненные строки колонки A и пишет в следующую строку через update range. Причиной, отражённой в комментарии и commit message, были особенности table detection у append endpoint.

Следствие: колонка A определяет занятость строки; параллельные append из нескольких клиентов могут выбрать одинаковую позицию.

## D-011. Задача может быть связана с календарём

- Статус: принято.
- Зафиксировано: 5 мая 2026, `92c5888` — `task_id` в work log, picker, schedule button и badge.

Чтобы поддержать несколько checklist items, схема эволюционировала до `task_ids`, сериализованных через `|` параллельно description. Tasks module строит даты планирования чтением work logs.

Следствие: отдельного schedule entity нет; календарная запись остаётся источником истины для планирования.

## D-012. Закупки являются самостоятельными сущностями со ссылкой на задачу

- Статус: принято.

Покупка хранится в листе `purchases`; `task_id` необязателен. Задача позволяет создать новые покупки, а purchases module управляет их статусом независимо.

Следствие: удаление задачи не удаляет покупку и сейчас оставляет dangling `task_id`.

## D-013. Исполнители вынесены в отдельный лист

- Статус: принято.
- Зафиксировано: 6 мая 2026, `175793c` — workers CRUD, settings management, task form/card.

Задачи хранят массив ID исполнителей, а имена находятся в `workers`. ID новых работников содержит code объекта.

Следствие: удаление worker не переписывает существующие задачи.

## D-014. Отдельный spreadsheet на объект

- Статус: принято.
- Зафиксировано: 6 мая 2026, `517f9ee` — multi-object support Variant A.
- `012b670`: автоматическое создание spreadsheet по имени.

Каждому объекту соответствует отдельная Google-таблица. Пользователь может создать новую таблицу через API или подключить существующий Sheet ID.

Следствие: переключение объекта требует полного сброса memory cache; cross-object отчётность отсутствует.

## D-015. Общий registry объектов для нескольких устройств

- Статус: эволюционировало.
- 7 мая 2026, `ea33a9e`: registry sheet и object code.
- `d57903f`: исправление cross-device corruption и force sync.
- `c8d15c7`: merge local-only объектов вместо перезаписи.

Registry `_registry` находится в legacy spreadsheet. При загрузке registry имеет приоритет для известных ID, но локальные неизвестные записи сохраняются и отправляются обратно.

Следствие: metadata объектов синхронизируется без отдельного backend, но full-list rewrite остаётся уязвимым к конкурентным обновлениям.

## D-016. Backup создаётся как новый spreadsheet через Sheets API

- Статус: принято с неполным restore.
- Зафиксировано: 5 мая 2026, `a79c11c` — create/restore/download и auto-daily backup.

Drive scope не запрашивается. Приложение читает листы, создаёт spreadsheet через Sheets API и записывает значения. Metadata последних десяти копий хранится в settings.

Следствие: старые spreadsheets не удаляются автоматически; текущий restore не восстанавливает workers и все settings.

## D-017. Порядок задач хранится числом с шагом 10

- Статус: эволюционировало.
- 10 мая 2026, `91f9f0d`: сортировка по order после создания.
- 22 мая 2026, `8469777`: новая задача получает `minOrder - 10` и появляется сверху.

Drag reorder сохраняет последовательность перенумерацией. Промежуток позволяет вставить новую задачу сверху без немедленной полной записи всех строк.

## D-018. Дата календарной записи изменяема, но конфликт запрещён

- Статус: принято.
- Зафиксировано: 22 мая 2026, `7ad1bf0`.

При изменении даты UI сначала проверяет отсутствие другой записи на целевой дате. Сохранение создаёт запись на новой дате и затем удаляет старую.

Следствие: операция двухшаговая и при сетевом отказе между шагами может оставить обе записи.

## D-019. Persistent access token и silent re-auth

- Статус: эволюционировало.
- 1 июня 2026, `3417d7f`: переход с session storage на localStorage, logout и silent re-auth.
- 7 июня 2026, `039782d`: 4-секундный fallback для mobile login hang.

Token переживает перезапуск браузера до истечения срока. Для известного email login page сначала делает `prompt: ''`; если мобильный браузер не возвращает ответ, loading снимается по timeout и пользователь может нажать кнопку.

Следствие: улучшен повторный вход, но увеличена поверхность риска при XSS.

## D-020. Нативный Canvas вместо chart dependency

- Статус: принято.

Stats module сам рисует bar и line charts через Canvas с учётом `devicePixelRatio`.

Следствие: внешняя chart dependency отсутствует. Текущий модуль сам задаёт отрисовку, размеры и обработку `devicePixelRatio`.

## Как добавлять новые решения

Добавляйте запись, если изменение:

- меняет границы модулей или источник истины;
- меняет схему Google Sheets;
- добавляет обязательную зависимость или build step;
- меняет OAuth/scopes/security assumptions;
- меняет hosting/deployment model;
- вводит несовместимость со старыми таблицами.

Запись должна содержать статус, контекст, решение, последствия и ссылку на commit после его появления.
