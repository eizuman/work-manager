# Модель данных Work Manager

## Источники состояния

Приложение использует три уровня состояния:

1. Google Sheets — постоянные предметные данные.
2. `localStorage` — OAuth-сессия, список и выбор объектов, локальная копия ставки и отметка авто-бэкапа.
3. Память страницы — кэш сырых строк в `sheets.js` и массивы активных UI-модулей.

Google Sheets является постоянным хранилищем работ, финансов, задач, тегов, закупок, исполнителей и синхронизируемых настроек. `hourly_rate` дополнительно кэшируется в `localStorage`; если значение из `settings` не загружено, UI использует локальное значение или fallback 700.

## Общие правила Google Sheets

- Каждый объект использует отдельный spreadsheet.
- Рабочий диапазон чтения — `<sheet>!A:Z` с `valueRenderOption=UNFORMATTED_VALUE`.
- Если первая ячейка первой строки буквально равна `id` без учёта регистра, строка считается заголовком и пропускается.
- Заголовки не обязательны для работы кода. Автоматически созданные spreadsheets создаются с пустыми листами без заголовков.
- Новая строка записывается в первую позицию после количества непустых строк колонки A.
- Запись выполняется с `valueInputOption=RAW`.
- Удаление выполняется физическим удалением строки через `deleteDimension`.
- `_rowIndex` добавляется только в объект в памяти и в таблицу не записывается.
- ID генерируются в браузере и не имеют серверного ограничения уникальности.
- Пустые или неизвестные дополнительные колонки справа игнорируются при чтении.
- Для пяти базовых предметных листов нет общего schema preflight или automatic ensure при подключении существующего Sheet ID. `_registry`, `workers` и `settings` имеют отдельные ensure-функции.

## Листы объекта

### `work_log`

Одна логическая запись на календарную дату. `saveWorkLog()` ищет существующую запись по `date`, а не по `id`, и обновляет первую найденную запись. Google Sheets не запрещает создать дубли даты вручную.

| Колонка | Поле | Формат | Значение по умолчанию / смысл |
|---:|---|---|---|
| A | `id` | string | Генерируемый ID; обязательный для попадания в выборку |
| B | `date` | `YYYY-MM-DD` | Календарная дата |
| C | `hours` | number | Десятичные часы; `0` для плана или note-only записи |
| D | `description` | string | Сериализованный чек-лист |
| E | `amount` | number | `hours × rate` на момент сохранения |
| F | `note` | string | Свободная личная заметка |
| G | `timestamp` | ISO 8601 string | Время последнего сохранения |
| H | `rate` | number | `parseFloat(value) || 700`; отсутствующее, нечисловое или нулевое значение читается как `700` |
| I | `task_ids` | pipe-separated string | ID задач по позициям чек-листа |

Формат `description`:

```text
первый пункт|✓выполненный пункт|третий пункт
```

Символ `✓` в начале означает выполненный пункт. `task_ids` содержит столько же логических позиций:

```text
taskA||taskC
```

Связь между текстом и задачей позиционная: `description[i]` соответствует `task_ids[i]`. Разделитель `|` и начальный `✓` не экранируются.

### `finance`

| Колонка | Поле | Формат | Значение / допустимые варианты |
|---:|---|---|---|
| A | `id` | string | Генерируемый ID |
| B | `date` | `YYYY-MM-DD` | Дата операции |
| C | `type` | enum string | `work`, `advance`, `payment` |
| D | `amount` | number | Положительная сумма операции |
| E | `balance` | number | Сохранённый накопительный баланс |
| F | `description` | string | Комментарий; для auto-work сейчас содержит дату `work_log` |
| G | `timestamp` | ISO 8601 string | Время создания/изменения |

В data layer сохранённый running balance увеличивается для `work` и уменьшается для `advance`/`payment`. Finance UI заново суммирует операции с обратной пользовательской семантикой: работа уменьшает показываемый баланс, выплаты увеличивают. После некоторых удалений сохранённые значения `finance.balance` не пересчитываются и могут отличаться от результата UI.

Автоматическое начисление связано с календарём условием:

```text
finance.type == "work" && finance.description == work_log.date
```

Стабильного `work_log_id` в схеме нет. Поэтому ручная операция типа `work` с описанием, равным дате, конфликтует с автоматической связью.

### `tasks`

| Колонка | Поле | Формат | Значение по умолчанию / варианты |
|---:|---|---|---|
| A | `id` | string | Генерируемый ID |
| B | `title` | string | Название, обязательное в UI |
| C | `description` | string | Свободное описание |
| D | `assignees` | comma-separated IDs | Ссылки на `workers.id` |
| E | `status` | enum string | `new`, `in_progress`, `done`; default `new` |
| F | `weather` | enum string | `sun`, `rain`, `any`; default `any` |
| G | `tags` | comma-separated IDs | Ссылки на `tags.id` |
| H | `order` | integer | Ручной порядок, обычно шаг 10 |
| I | `created_at` | ISO 8601 string | Время создания |
| J | `completed_at` | ISO 8601 string или пусто | Устанавливается при переходе в `done` |

Новая задача получает `min(existing order) - 10`, поэтому появляется сверху. Полная сортировка перенумеровывает видимые ID значениями `10, 20, 30, ...`.

### `tags`

| Колонка | Поле | Формат | Значение |
|---:|---|---|---|
| A | `id` | string | Генерируемый ID |
| B | `title` | string | Название тега |
| C | `created_at` | ISO 8601 string | Время создания |

Цвет не хранится: CSS-класс `tag-color-0..7` вычисляется детерминированным hash от ID.

### `purchases`

| Колонка | Поле | Формат | Значение по умолчанию / варианты |
|---:|---|---|---|
| A | `id` | string | Генерируемый ID |
| B | `title` | string | Наименование, обязательное в UI |
| C | `price` | number | Стоимость, default `0` |
| D | `status` | enum string | `pending`, `bought`; default `pending` |
| E | `task_id` | string или пусто | Ссылка на `tasks.id` |
| F | `created_at` | ISO 8601 string | Время создания |
| G | `bought_at` | ISO 8601 string или пусто | Устанавливается при переходе в `bought` |

### `workers`

| Колонка | Поле | Формат | Значение |
|---:|---|---|---|
| A | `id` | string | Prefixed ID вида `w_<object-code>_<random>` |
| B | `name` | string | Имя исполнителя |
| C | `active` | string boolean | Только точная строка `false` читается как false |
| D | `created_at` | ISO 8601 string | Время создания |

При отсутствии листа `workers` он создаётся перед первым добавлением исполнителя. `getWorkers()` при любой ошибке чтения возвращает пустой массив без вывода причины пользователю.

### `settings`

| Колонка | Поле | Формат | Значение |
|---:|---|---|---|
| A | `key` | string | Ключ настройки |
| B | `value` | scalar/string | Значение |

Известные ключи:

| Ключ | Формат | Назначение |
|---|---|---|
| `hourly_rate` | number | Текущая ставка объекта |
| `backups` | JSON string | До 10 metadata-записей `{id,date,time,title}` |

Лист создаётся перед первой записью настройки. Ошибка чтения логируется в console, после чего `getSettings()` возвращает `{}`.

## Registry объектов

Лист `_registry` находится не в spreadsheet активного объекта, а в константной legacy-таблице.

| Колонка | Поле | Формат |
|---:|---|---|
| A | `id` | string вида `obj_<random>` |
| B | `name` | string |
| C | `sheetId` | Google spreadsheet ID |
| D | `createdAt` | ISO 8601 string |
| E | `code` | короткий base36 code |

Registry не имеет заголовка. При сохранении диапазон `A:E` полностью очищается и список записывается заново. При загрузке записи без `id` или `sheetId` отбрасываются.

Локальные объекты, отсутствующие в registry, сохраняются при merge и затем фоново дописываются полной перезаписью registry.

## `localStorage`

| Ключ | Формат | Назначение |
|---|---|---|
| `access_token` | string | OAuth access token |
| `token_expires_at` | integer string | Unix time в миллисекундах |
| `user_email` | string | Email последнего вошедшего пользователя |
| `user_name` | string | Имя пользователя |
| `objects` | JSON array | Локальная metadata объектов |
| `activeObjectId` | string | Выбранный объект |
| `hourly_rate` | number string | Локальный кэш текущей ставки |
| `last_auto_backup` | `YYYY-MM-DD` | Дата последнего успешного auto-backup в браузере |
| `object_code` | string | Legacy fallback для генерации prefixed ID; текущий код читает этот ключ, но не записывает его |

`signOut()` удаляет только auth-ключи; объекты, ставка и backup metadata остаются локально.

## Связи и целостность

```text
workers.id ──< tasks.assignees[]
tags.id ─────< tasks.tags[]
tasks.id ────< purchases.task_id
tasks.id ────< work_log.task_ids[]
work_log.date ── finance.description  (только type=work, неформальная связь)
```

Связи прикладные, а не ограничения Google Sheets. Текущий код не выполняет каскадное удаление:

- удаление задачи оставляет ссылки в календаре и закупках;
- удаление тега или исполнителя оставляет ID в задачах;
- удаление покупки или календарной записи не меняет задачу.

UI частично переносит dangling references: неизвестный тег скрывается, неизвестный worker показывается как ID, отсутствующая задача у покупки не отображается.

## Чтение, кэш и запись

`readSheet()` кэширует массивы `{values, rowIndex}` по имени листа. После `updateRow()` и `deleteRow()` кэш листа удаляется. `invalidateCache()` без аргумента также очищает metadata numeric sheet IDs.

При переключении объекта вызывается полная invalidation, что важно, поскольку ключ кэша не включает spreadsheet ID.

Многошаговые изменения не являются транзакционными. Например:

- сохранение календаря и синхронизация finance;
- создание задачи и нескольких закупок;
- создание backup spreadsheet и запись его metadata;
- полная перезапись registry.

При сбое между шагами возможна частично обновлённая модель.

## Даты и время

Календарные поля хранятся строками `YYYY-MM-DD`, timestamp — строками `Date.toISOString()`. Несколько значений «сегодня» также строятся через `toISOString().slice(0, 10)`, то есть по UTC, тогда как календарный UI частично использует локальные компоненты `Date`. Единой функции локальной календарной даты в текущем коде нет.

## Бэкап и восстановление

Backup читает листы:

```text
work_log, finance, tasks, tags, purchases, workers, settings
```

и создаёт новый spreadsheet с теми же листами. Список последних десяти backup ID хранится в `settings.backups`; более старые spreadsheets автоматически не удаляются.

Restore заменяет только:

```text
work_log, finance, tasks, tags, purchases
```

Из `settings` отдельно восстанавливается `hourly_rate`. `workers`, остальные settings и registry не восстанавливаются. Это текущее ограничение, а не полный mirror restore.

## Изменение схемы

Любое добавление/перестановка колонок требует:

1. сохранить чтение старых строк;
2. определить default для отсутствующей ячейки;
3. обновить row-to-object и object-to-row функции;
4. учесть backup/restore/export;
5. описать миграцию в этом документе;
6. проверить существующую таблицу с заголовками и автоматически созданную таблицу без заголовков.

Это требования совместимости текущего формата, а не существующая автоматическая система миграций: versioned migrations в коде отсутствуют.
